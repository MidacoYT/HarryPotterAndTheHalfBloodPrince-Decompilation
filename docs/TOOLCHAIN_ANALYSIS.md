# HP6 toolchain investigation

Audit date: 2026-10-09. Target: the user's installed Windows PC executable, `hp6.exe` version 1.0.0.1. All hashes below identify that exact file; results should not be generalized to other regional or patched builds.

## Findings

**Best-supported identification: Microsoft Visual C++ 8.0 / Visual Studio 2005 x86, build 50727, with high confidence.** The compiler and linker Rich records, PE linker field, and VC80 CRT manifest corroborate the VS2005 family. Microsoft documents both compiler revisions `14.00.50727.42` (initial release) and `14.00.50727.762` (SP1); the PE Rich records cannot distinguish them. The `.762` CRT manifest identifies the deployed runtime assembly, not necessarily the compiler used. Original compiler/linker command lines, SDK revisions, and EA's build machine remain unknown.

This is a toolchain-family identification, not proof that every HP6 function was compiled by `14.00.50727.42` or `.762`. A separate experiment below proves both VC8 revisions can produce one 291-byte HP6 function body exactly from ordinary C. It does not prove EA used either exact revision or those flags for that function.

Compiler-family evidence:

1. The PE optional header records linker version **8.00**. This is consistent with Microsoft Visual C++ 8.0, but the two-byte PE field is only a family-level clue.
2. The executable imports **MSVCR80.dll** and **MSVCP80.dll**, including `__CxxFrameHandler3`, `_CxxThrowException`, and VC++ decorated standard-library symbols. The embedded `RT_MANIFEST` requests `Microsoft.VC80.CRT` version **8.0.50727.762**, x86. This strongly identifies the VC8 runtime family and its deployed servicing version; it does not by itself identify the compiler that emitted the game code.
3. Decoding the DOS-stub Rich header gives these build 50727 records: C compiler x21 (`0x6d`), C++ compiler x182 (`0x6e`), MASM x23 (`0x7d`), linker x1 (`0x78`), resource compiler x1 (`0x7c`), Utc1400_LTCG_CPP x27 (`0x72`), and import-library tool x6 (`0x7b`). The linker product ID is `0x78`; PE linker version 8.00 disambiguates this from other releases that reused build 50727. The mapping follows the published [Rich header product-ID table](https://github.com/dishather/richprint). Its documentation notes that library object inputs contribute records too, so counts are not counts of HP6 source files.
4. The Rich header also contains C/C++/import records for VS2003 build `3077` and Windows Server 2003 SP1 DDK build `4035`, plus `0x7e/build 50327`. For build 4035 the counts are four C objects (`0x5f`), one C++ object (`0x60`), and 23 import-library objects (`0x5d`); the latter are not compiled game functions. The C/C++ entries show that a small number of DDK-built objects entered the link, not that the game itself was built with the DDK compiler. I checked the VC8 RTM `oldnames.lib`: all 280 COFF members carry `@comp.id = 0x007ec497` (product ID `0x7e`, build 50327). Independent decoders classify this as the VC8 `AliasObj` compatibility tool used by `oldnames.lib`, rather than a C/C++ compiler record. The target count of eight is therefore consistent with selected old-name alias members from a library. This removes the apparent VS2005-beta compiler clue; it does not prove which exact copy or servicing revision of `oldnames.lib` was linked. Rich data is unsigned and can be rewritten; its agreement with other evidence makes the VC8 conclusion substantially stronger than any single clue.
5. No PDB path, CodeView `RSDS`/`NB10` record, or exports were found. The PE therefore provides no direct original PDB or named build configuration. In particular, no `.pdb`, `.ilk`, `.map`, project, or solution files for the game are present in the repository or matching workspace; only toolchain/runtime PDBs are available.
6. File version and PE timestamp are compatible with a January 2009 build, but neither encodes the compiler revision.
7. `IMAGE_FILE_RELOCS_STRIPPED` is set in file characteristics (`0x0103`), no base-relocation directory exists, and DLL characteristics are `0x0000`. Microsoft's [`/FIXED` documentation](https://learn.microsoft.com/en-us/cpp/build/reference/fixed-fixed-base-address?view=msvc-170) says `/FIXED` is the default for EXE projects and suppresses relocation data. A controlled VC8 link probe produced the same stripped-relocation characteristics with default options and explicit `/FIXED`; the PE supports default fixed-base behavior but cannot show whether EA explicitly passed `/FIXED`.

The nonstandard `.1911` section is 262,144 bytes virtual, 260,276 bytes raw, and has `0xE00000E0` characteristics (read/write/execute and code/data flags); raw entropy is about 6.39 bits/byte. It contains executable-looking bytes. The section name matches the Razor 1911 release-group name. Secondary installation reports for this game describe replacing the installed executable with a `hp6.exe` from a Razor1911 folder, and a public file-info page reports the same MD5 as this installed file. This makes a modified/no-disc image plausible, but does not prove that this section was added by that group or identify the original retail bytes. Until compared against a verified retail executable, conclusions apply to this installed image, not necessarily the untouched master executable.

## Runtime linkage and servicing evidence

The executable imports both `MSVCR80.dll` and `MSVCP80.dll`, and its embedded side-by-side manifest requests the x86 assembly `Microsoft.VC80.CRT` version `8.0.50727.762`. The verified SDK payload extracted outside the repository includes the corresponding retail DLLs; their SHA-1 values match the nested digest values in that payload's assembly manifest: `msvcr80.dll` `9fd3a7f0522d36c2bf0e64fc510c6eea3603b564`, `msvcp80.dll` `d0a27f553c0fe0e507c7df079485b601d5b592e6`, and `msvcm80.dll` `609b81fbd3acda8c56e2663eda80bfafc9480991`. This cross-check validates the local `.762` runtime candidate and is consistent with the target's runtime dependency; it does not establish that those exact DLL file bytes were installed with the game.

The imports are strong evidence that the program uses the dynamic VC8 C and C++ runtimes. That makes release `/MD` linkage the best explanation; Microsoft's option documentation maps `/MD` to the DLL runtime import libraries ([`/MD` reference](https://learn.microsoft.com/en-us/cpp/build/reference/md-mt-ld-use-run-time-library?view=msvc-170)). The PE does not preserve the compiler command line, so `/MD` remains an inference rather than a recovered flag. The target does not import debug CRT DLL names, consistent with a retail configuration. Dynamic CRT linkage narrows the runtime model but cannot distinguish compiler `.42` from `.762`: a program compiled with either could link against the `.762` runtime assembly.

A separate DDK lead explains those build-4035 records. The Windows Server 2003 SP1 DDK is version `3790.1830`; contemporaneous developer references identify its x86 compiler as `13.10.4035` ([OSR discussion](https://community.osr.com/t/compiler-version-not-supported-by-windows-ddk/22551)). The original DDK ISO link on Microsoft's download host remains live; it returned a 242,141,184-byte ISO, SHA-256 `7a27263e4c3c89dee113eba75dc9145bf7019b43a2c5e24bc9382dbde79f7f8b`, volume label `RTM`. This is a locally recorded hash, not a Microsoft-published checksum. The included EULA limits the software license to designing, developing, and testing drivers for the listed Microsoft Windows products. Since this investigation compiles game code rather than drivers, I did not install, extract, or run its compiler; the ISO was unmounted and removed after checking its EULA and file inventory. Thus build 4035 is identified from the Rich product IDs and historical version records, but no DDK code-generation comparison was attempted. This small DDK footprint remains consistent with prebuilt library/object inputs to the VC8-linked executable.

## Historical and provenance research

Microsoft's official page for the [Windows SDK Update for Windows Vista, February 2007](https://www.microsoft.com/en-us/download/details.aspx?id=14477) states that its C++ compilers are the same compiler versions shipped with Visual Studio 2005 SP1, and publishes the ISO size and SHA-1. A copy already present outside this repository at `D:\HP\reconstruction\matching\downloads\vista-sdk.iso` is 1,237,436,416 bytes and hashes to `5d28463daaa755450d697c850dd622d1f8b580ae`, matching Microsoft's published verification value. Its recorded source URL is Microsoft's download host.

Microsoft's archived [C++ team blog](https://devblogs.microsoft.com/cppblog/what-compiler-does-the-compiler-team-use-and-decoding-version-numbers/) explicitly distinguishes the original compiler (`14.00.50727.42`) from SP1 (`14.00.50727.762`), and Microsoft's [Windows SDK compiler table](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/cc307395%28v%3Dmsdn.10%29) lists compiler `.42` alongside linker `8.00.50727.762`. Thus a mixed `.42` compiler / `.762` linker toolchain was a supported historical configuration; the target's `.762` runtime manifest cannot resolve the compiler version.

The Rich header also records VC7.1-era products (build 3077) and older DDK products (build 4035), in addition to VC8 build 50727. Those records make prebuilt third-party libraries a plausible source of older build records; they do not override the PE linker 8.00, the large VC8 C/C++ records, or the VC80 CRT manifest as evidence for the main executable build. I checked the historical [Microsoft Visual C++ Toolkit 2003](https://groups.google.com/g/microsoft.public.vc.language/c/8MmBk6_Ply8), which provided the VC7.1 command-line compiler. Its original Microsoft download URL now returns 404. Two signed mirrors were examined: the April package has version resource `1.00.0000`, size 32,952,488, SHA-1 `956c81c3106b97042c4126b23c81885c4b5211f4`, and SHA-256 `03aad135c22e953e0928b118705338afdbd08abf8e4039038ef77945504e65fa`; the June package has version resource `1.01.0000`, size 32,948,392, SHA-1 `50dc6cca1503f08a41d56816f3f1abcaf347b0bd`, and SHA-256 `c040f6ffbc2259426dd523b7561575fe1704b58bc37092fbfe27b64aefc449f6`. Both have valid Microsoft Authenticode signatures with VeriSign timestamps, and hashes match historical checksum records. Microsoft's archived Toolkit release notes say version 1.01 (July 6, 2004) updated the compiler to `13.10.3077`, exactly the VS.NET 2003 build; version 1.0 had slightly different compiler build numbers. This makes the June package a credible source of the VC7.1 build-3077 Rich records, but not proof those particular objects came from it. The archived Toolkit EULA permits use for internal work and for designing, developing, testing, demonstrating, and evaluating software, with separate conditions on redistribution. Portable extraction of the signed June bootstrapper exposed its MSI without installing it; MSI extraction yielded `cl.exe` 13.10.3077 (SHA-256 `2ecf86a3edfd3deae498e08298e210e984537ce9e11759930561e43f40bd2515`) and `link.exe` 7.10.3077 (SHA-256 `0d5f9712d0da843d787bf4ce4e678abc6b737940996706b2c86101eac9df3e3c`). The payload executables are not individually signed; their provenance is tied to the Microsoft-signed, hash-verified setup package. No package was installed. The extracted VC7.1 tools were then used for direct code-generation tests below.

## Controlled code-generation experiments

All comparisons below use function bytes extracted from the pinned installed executable. For the 291-byte case, a local C candidate from the separate `D:\HP` research workspace was compiled in place; the source and compiler were not copied into this repository. Its source SHA-256 is `2613dca0fae6a007c30fb0e3b410615cd339bccaba9118aae0f9aad4a6ba62a1`.

### Exact body at `0x0054D990`

This is a nontrivial object-initialization routine with dozens of member stores, not a return-only stub. Its C candidate compiles to a 291-byte `.text` body. The direct executable slice at `0x0054D990` is also 291 bytes, and both hash to `0d492295fc81107cf2309212b1acd6204254e2946bb422b7fbee5bf82edce7fd`. A byte-for-byte comparison found zero differences and no relocations.

| Compiler | Options | Candidate bytes | Result |
| --- | --- | ---: | --- |
| MSVC 14.00.50727.42 (VC2005 RTM) | `/TC /GS- /Gy /we4013 /FI scalar_aliases.h /O1` | 291 | exact |
| Same | same, `/O2` | 291 | exact |
| Same | same, `/Ox` | 291 | exact |
| Same | same, `/Od` | 643 | not exact |
| MSVC 14.00.50727.762 (VC2005 SP1-era) | `/TC /GS- /Gy /we4013 /FI scalar_aliases.h /O1` | 291 | exact |
| Same | same, `/O2` | 291 | exact |
| Same | same, `/Ox` | 291 | exact |
| Same | same, `/Od` | 643 | not exact |
| MSVC 14.44.35207 (VS2022) | same, `/O1` | 291 | exact |
| Same | same, `/O2` or `/Ox` | 481 | not exact |
| Same | same, `/Od` | 917 | not exact |

Both VC8 RTM (`14.00.50727.42`) and SP1 (`14.00.50727.762`) produce this nontrivial 291-byte HP6 body exactly under `/O1`, `/O2`, and `/Ox`; both produce the same 643-byte mismatch under `/Od`. Modern MSVC also matches under `/O1`. This verifies that both historical VC8 revisions can generate the body from ordinary C, but this sample cannot distinguish the compiler revision or recover whether EA used `/O1`, `/O2`, or `/Ox`.

### Cross-check against a function in this repository

The current `src/fn_004DA3D0.c` candidate was compiled with VC8 `/TC /O2 /GS-`. It produced 38 bytes versus the 36-byte target and objdiff reported a 52% match. The current C expression therefore does **not** reproduce that function under VC8. This negative result is retained to prevent the 291-byte success from being misread as a general match rate.

#### RTM versus SP1 code-generation differential

I compiled the 1,925 C candidates already present in `src/` with both signed VC8 compilers using `/O1 /GS-` and `/O2 /GS-`. Each revision produced 1,915 objects; ten sources failed to compile in both environments. Across all 1,915 paired outputs, `.text` bytes and raw relocation records were identical for each matching option set. Exact matches against expected COFF bodies were also identical across revisions: 154 source bodies under `/O1`, and 193 under `/O2`; 144 matched under both, ten only under `/O1`, and 49 only under `/O2`. Every per-function verdict was the same between RTM and SP1. `/O2` yields more matches in this candidate corpus, but the candidates are reconstructed pseudocode and are not evidence of EA's global build flag. This dataset does not identify `.42` versus `.762`; it shows their generated code is indistinguishable for the tested sources and option sets.

I extended the patch comparison to C++ using 147 previously exact C++ source/option variants (the 81 exact candidates from the C++ pass and 66 exact variants from its flag sweep). I recompiled each source with RTM using the same optimization variant, located the compiler-decorated function symbol, applied the recorded external-address relocations, and compared the resulting bytes against the pinned executable slice. All 147 compiled; all 147 remained byte exact, with no comparison errors or mismatch. The test uses reconstructed C++ declarations and layouts, so it verifies servicing-revision codegen for those candidate inputs, not the original EA source or global project settings. It provides no `.42` versus `.762` discriminator.

A further targeted x86 comparison exercises 12 unsigned 64-bit integer forms (loads/stores, assignments, arithmetic, shifts, comparisons, and a conditional update) with both VC8 compilers. All 36 compiler/option pairs (`/O1`, `/O2`, `/Ox`) emitted identical function bodies. The objects are standard i386 COFF; the target remains PE32 x86. This is relevant because Microsoft's [SP1 backend fix summary](https://devblogs.microsoft.com/cppblog/vc2005-sp1-bug-fixes-back-end/) lists, among other issues, incorrect optimized 64-bit assignment code in 32-bit mode. Our simple probes do not recreate that specific historical bug report, so they neither identify `.42` nor `.762` in HP6; they only show that these representative x86 forms do not discriminate them. The compiled objects and full byte records are in `D:\HP\reconstruction\matching\toolchain\differential-scan\vc8_64bit_probes`.

#### VC7.1 (Toolkit 2003) differential against reconstructed C++ bodies

The 291-byte function at `0x0054D990` also compiles byte-exactly with VC7.1 under `/O1`, `/O2`, and `/Ox`, so that function alone cannot distinguish VC7.1 from VC8. A more discriminating sample was the set of 147 reconstructed C++ source/option variants that were already exact under VC8 SP1. VC7.1 compiled 106; 82 remained exact and 24 differed. The other 41 failed to compile, primarily because VC7.1 rejects the `__thiscall` extension used by these candidates. The compiler also warns that `/GS-` is unknown; it is ignored, and the Toolkit compiler does not emit a stack cookie by default.

I swept `/O1`, `/O2`, `/Ox`, and `/Od` for each of those 24 mismatches (96 successful builds). Fourteen addresses matched in at least one of those baseline modes, all under `/O1`; ten stayed different under all four: `0x004DA3D0`, `0x004EEF80`, `0x0050D880`, `0x00582110`, `0x005BEAE0`, `0x005E4080`, `0x005EC5E0`, `0x00632090`, `0x0068C340`, and `0x006E0C52`. I then tried eight additional common optimization combinations on each remaining address (80 successful builds): `/O1 /Oi`, `/O2 /Os`, `/O2 /Ob0`, `/O2 /Oy-`, `/O2 /Ot`, `/O2 /Oi`, `/Ox /Oi`, and `/Ox /Os`. None matched.

These are meaningful negative results for VC7.1: the current reconstructed C++ inputs that VC8 reproduces include bodies VC7.1 does not reproduce across this option sweep. They favor VC8 as the main compiler for the tested game code and make VC7.1 more plausible as the origin of older library/object records. They do not prove the original source, declarations, or build flags; a mismatch can arise from reconstruction differences, and untested VC7.1 switches remain possible. Full commands, outputs, and object files are retained outside the repository under `D:\HP\reconstruction\matching\toolchain\differential-scan\cpp_vc71`, `vc71_opt_sweep`, and `vc71_flag_sweep`.

## Linker, SDK, and options: unresolved

* The PE header says linker version 8.00 and Rich product `0x78` identifies linker build 50727. The local Microsoft-SDK candidate reports `8.00.50727.762`. Microsoft documentation confirms `.762` was paired with the `.42` compiler in at least one SDK configuration; exact compiler and linker servicing revisions remain unproven. No complete game link was run.
* The executable is fixed-base and consistent with the VC8 EXE default `/FIXED`; whether EA passed `/FIXED` explicitly is not recoverable from the header. Its preferred image base is `0x00400000`, consistent with the x86 default. No evidence recovers the original `/OPT`, `/DEBUG`, `/INCREMENTAL`, `/LTCG`, `/SECTION`, or `/BASE` arguments. A matching probe linked by the authenticated RTM `link.exe` also has `IMAGE_FILE_RELOCS_STRIPPED` (`0x0103`) and no relocation directory both with default options and explicit `/FIXED`; this still cannot reveal whether the game build passed that option.
* A second controlled linker test compiled one small C entry point once with RTM and linked the same COFF object using both VC8 linkers with identical `/SUBSYSTEM:CONSOLE /ENTRY:mainCRTStartup /NODEFAULTLIB /FIXED` options. Both produced 1,024-byte PE files with identical SHA-256 (`87a3682148217467e7c3160ca8076f184999272c7cb242b6051dc12f5098f37f`) and zero differing bytes. This probe does not reproduce HP6's full object graph or linker switches, so it cannot distinguish the game's linker patch.
* Section layout, `.1911` permissions, timestamp, imports, runtime version, and Rich header do not reveal `/OPT`, incremental-link settings, function ordering, PDB, or whole-image signing/packing settings conclusively. The 27 `Utc1400_LTCG_CPP` records indicate LTCG-generated C++ inputs, but do not quantify their surviving contribution or recover every linker option.
* DirectX 9 imports identify APIs only. The 513 embedded D3DX shader compiler tags identify metadata in shader blobs, not the SDK used to compile the executable or its linked libraries.
* Historical public sources identify EA Bright Light as the developer, and secondary game catalogs label its engine "Bright Light Halogen". No primary source located in this search identifies the studio's PC compiler, linker, SDK, or project flags. The engine label is not evidence of a specific toolchain.
* `dumpbin`, IDA Pro, Ghidra, PE-bear, and Detect It Easy are not on the active tool search path. No IDA MCP endpoint was exposed in this session. PE checks were performed by `tools/audit_pe.py` and small standard-library parsers; objdiff-cli 3.8.2 is installed. The existing `hp6.exe.i64` is present beside the game, but no edits were made to that database.

## Conclusion and next evidence needed

Visual C++ 8.0 / Visual Studio 2005 x86 build 50727 is strongly identified and experimentally capable. Both authenticated compiler patches available here (`.42` RTM and `.762` SP1) reproduce multiple function bodies exactly, and the tested source corpus shows no patch-specific output difference. The target therefore does not yet distinguish compiler revision, linker servicing revision, original compiler flags, original linker flags, or SDK revisions. The `.1911` section also leaves the target image retail/protection-modified provenance unresolved. Do not report the complete original toolchain as conclusively identified.
